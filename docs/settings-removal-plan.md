### Confirmed settings scope

- F1 is the complete set of independently configurable PC game features. The INI stores supported preferences for F1. It does not offer extra gameplay, rendering or input features. Removing a feature means removing its config readers, overrides, branches, exclusive hooks, generated patches or shader paths, and installer or launcher exposure as applicable. Retired names may remain in migration metadata only.
- Remove the Console Mode selector and its configuration. Report the existing Docked/Boost profile to the game by default. Output and scene sizing belong to the PC renderer. Controller layout and glyph selection are independent of that profile. This decision does not call for redesigning handheld behavior.
- Remove current shadow controls and their exclusive implementations, including `shadow_res`, `shadow_scale` and `shadow_range`. Remove filter adjustments used specifically for runtime scaling. Preserve stock shadows and required device correctness, and evaluate any shared shader behavior by its actual consumers.
- Keep the anisotropic filtering override. DLSS is the only upscaler and frame-generation backend in the first version of the reworked overlay. Both controls and the performance overlay include Off. Retire FSR and other frame-generation backends from that scope, including their exclusive code and hidden switches. Preserve native rendering on supported AMD and NVIDIA GPUs. XeSS upscaling, XeSS-FG and XeLL are later work. Automatic aspect ratio is the default, with the Force Original behavior described above.
- Controller type controls layout and glyphs. Keep the jump/attack swap and independent stick dead-zone overrides as described below. Preserve the Ocarina microphone, the F1 mouse cursor and basic keyboard testing.
- Installation paths, setup and save tools are separate from PC game feature settings. Developer diagnostics may collect evidence through their own tooling. A switch that changes the retail rendering or gameplay algorithm is not a diagnostic exemption merely because a benchmark uses it.

## Approved scope and boundaries

The user approved removing reduced texture detail, the descriptor restrictions required by that reduction, normal runtime conversion of static textures after installer preparation replaces it, unsafe partial writeback, current one-frame-ahead replay, invasive camera sensitivity modification, external limiter management, selectable bloom insertion, HDR output, PCSS and co-op. The user also approved retiring the obsolete features listed below and fixing configuration defects.

Approval of this direction is not approval of an unfinished migration algorithm or resource-core design. Those contracts must be reviewed before the affected implementation starts.

The following remain supported unless explicitly changed later:

- The game's original detail and mip levels, original shadow behavior, SDR lighting and tone mapping.
- DLSS reconstruction and frame generation, including their required inputs and output paths during HDR and bloom cleanup.
- Correct CPU/GPU visibility, resource ownership, image aliases, texture views and GPU completion lifetimes.
- Worker recording, safe asynchronous preparation, current separate presentation, and correct selective/deferred transfers.
- Native controller behavior, the game's sensitivity options, button mappings and glyphs, keyboard testing input and the F1 mouse cursor.
- Personal saves, save import/export, old backups and all four benchmark saves.
- Compact timing records, relevant diagnostic probes and route verification.
- Unrelated features and compatibility paths. An audit finding is not blanket permission to delete every nearby subsystem.

The governing objective is faster complete resource handling and earlier delivery of correct GPU work, with stable frame pacing and long-session behavior. Reuse is one means. Judge each design by its connected effects, including downstream operations it enables removing and costs it introduces elsewhere. A 0.01 ms validation step that avoids only 0.001 ms locally can still be worthwhile if its result eliminates 0.3 ms downstream. Neither isolated timings, avoided-operation percentages nor FPS alone determine whether an architectural step is worthwhile. Unfinished dependencies must be explicit, not an indefinite promise of future benefits.

## User requirements and targets recorded on 18 November

These requirements guide the cleanup and future core design. They do not select a core implementation. Hard product requirements, desired hardware targets and unproven performance targets are distinguished below so an aspiration is not silently turned into a claimed capability.

1. **Frame-rate independence is required.** The game must be playable at arbitrary practical rendered frame rates. Simulation speed, physics, animation, camera, input, audio and scripted events must not depend incorrectly on render frequency. Variable intervals matter as well as a stable high FPS. Generated frames are presentation output, not extra simulation steps. Exact supported bounds and behavior after a long pause still need definition; arbitrary does not mean physically unlimited throughput.
2. **DLSS reconstruction and DLSS frame generation are primary features.** Treat their inputs, resource lifetimes, scheduling and presentation requirements as part of the initial design. Initial backend scope follows the confirmed F1 settings above. AMD and NVIDIA must both have fully working supported rendering. Expose vendor-specific features only where supported. Assess FG overhead using rendered FPS, pacing and latency separately from the displayed frame rate.
3. **Motion vectors are an initial design requirement.** Plan stable identity, previous/current transforms and deformation inputs, camera history, jitter, depth and ownership from the beginning. Static objects, rigid animation, skinned characters/equipment, cloth and material animation need explicit coverage decisions. History for pixels without reliable correspondences needs a defined policy. Resource management enables valid data; it does not generate every material's correct motion by itself.
4. **Controller QoL remains supported.** Alternate controllers, mapping and appropriate in-game glyphs must continue to work. Preserve the existing features while reconciling any separately developed UI changes.
5. **Microphone Ocarina input remains supported.** Keep capture, permission/device handling and the game's audio-input behavior. Cleanup must not remove shared audio/input facilities with co-op or camera code. Audio timing and microphone availability must remain correct at variable frame rates.
6. **Consistent frame pacing is a hard requirement.** Avoid bursts, unnecessary stalls and progressively worsening sessions. Measure simulation/render completion and display cadence separately, with FG on/off. A stable average cannot excuse repeated visible stalls. Quantitative acceptable hitch frequency and duration remain to be agreed; absolute immunity to OS/driver interference cannot be guaranteed.
7. **Reduce sustained performance variation.** The Kakariko example of roughly 80 FPS in one view and below 60 in another is a target for improvement. Improve the slow view through useful-work reduction, scheduling and bounded preparation; do not satisfy consistency by slowing the fast view or silently lowering image quality. Intrinsic differences in scene work remain possible.
8. **16 GB system RAM is a hard supported gameplay configuration.** Around 8 GB for the game is the desired application-memory target, with wiggle room. Budget for the OS, driver and reasonable headroom rather than treating installed capacity as fully available. Define steady-state and transition peaks separately. Track process committed memory and resident working set, staging/driver overhead and system pressure; low resident memory caused by paging is not success. The installer must also work on a 16 GB system, ideally without a large time penalty, but has a separate adaptive budget: it may use substantially more memory on larger systems when that meaningfully speeds preparation. The gameplay application-memory target is not a universal installer cap.
9. **8 GB VRAM and 16 GB system RAM must accommodate a comfortable 1080p60 experience when processing power is sufficient.** Memory capacity and management must not prevent that target. DLSS reconstruction belongs within this envelope on supported NVIDIA hardware; AMD needs an independently valid supported rendering configuration. Frame generation is explicitly not required to fit this minimum budget. Do not silently require an aggressive upscaling mode to claim support: define the native and reconstructed test configurations later. Higher output resolutions and FG may require more memory. System RAM and dedicated VRAM are distinct pools on a discrete PC; their capacity cannot simply be compared with a console's unified pool. Lower internal resolution reduces many render-target sizes, but DLSS also adds its own buffers/history, so total VRAM savings must be measured rather than assumed.
10. **Additional memory should improve the experience.** On 32 GB system RAM or 16 GB-plus GPUs, useful retained assets/history and bounded prefetch can reduce reloads and preparation. Admit extra cached data only when it has an expected benefit, release it under pressure, and avoid proportional worker/scratch growth that consumes all newly available headroom. Preserve one visual-quality baseline across capacity tiers.
11. **Broad resolution and aspect support is required throughout rendering.** Support practical arbitrary sizes within hardware/API limits, covering 16:9, 21:9 and 16:10; target 32:9 as well. The minimum supported output includes 1280x720, with lower internal rendering allowed for upscalers. A 1080p output must not inherit an unexplained 1440p minimum scene allocation. Classify targets by purpose: render-sized, output-sized, relative-resolution effects, or independently sized resources. Preserve necessary independent sizes rather than shrinking every texture blindly. Scale resolution-dependent effects, sampling offsets, jitter/motion/depth dimensions and reconstruction inputs coherently. Projection alone is insufficient for aspect support: visibility and occlusion culling, shadow/light coverage, screen-space effects, HUD/glyph layout, menus and resizing must remain correct outside 16:9. Deliberate movie/cutscene framing requires a policy rather than stretching or assuming unseen content exists. Very wide/high-resolution output need not fit the minimum-memory envelope.
12. **Seamless automatic adaptation is a core requirement.** Supported hardware should receive safe policies without enabling a checkbox, selecting a memory tier or manually tuning ownership, writeback, worker counts or cache correctness. Distinguish installed capacity from current available physical memory, system commitment headroom and GPU memory budget/usage. Installed capacity supplies context and limits; changing availability and pressure govern discretionary work and retention. Expose genuine preferences and explain unavailable features. Automatic selection must not silently change an explicitly chosen reconstruction mode or image quality to conceal a failure.
13. **Reduce the cost of the connected resource-handling chain.** Track resource identity, content and interpretation changes so relevant consumers can depend on established facts. Reuse, verification and retention are worthwhile when their combined downstream benefits exceed their total processing, synchronization and memory costs; an individual step need not be cheaper in isolation. Hashing, scanning or copying may be justified parts of that design, but their full cost and frequency must be included rather than hidden behind hit counts. Keep retention bounded and record why an item was invalidated or rebuilt.
14. **90-plus rendered FPS at the 1% low on a 7800X3D is an ambitious performance target.** This implies roughly an 11.1 ms frame budget, but has not been established as attainable across the whole game. Define GPU, output/internal resolution, feature set and workload. Preserve all-frame 1% lows including hitches; additionally report a separately defined sustained-workload measure and a hitch report. Never remove slow frames after seeing results to claim this goal. FG-generated FPS does not satisfy this rendered-FPS target.
15. **Avoid compilation stalls during normal play.** Installation/preparation should cover known game and active fork shader/pipeline recipes, with valid reuse across sessions. Unexpected content/variants need a defined, nearly invisible policy where possible. Compiled shader programs alone do not prove that every runtime pipeline is prepared. Cold installation, warmed play, driver/cache invalidation and content updates require separate acceptance checks. The user permits narrowly scoped temporary cosmetic fallbacks for rare remaining misses under the preparation policy below; this does not authorize generalized skip-draw behavior.
16. **Keep shader/pipeline storage and memory efficient.** Deduplicate by compatible identity, prepare only active required variants, bound retained data, and remove obsolete recipes from enumeration. Use lossless storage compression where it produces a net benefit without loading giant expanded copies during play. Do not minimize file count/size by invalidating useful work on every build.
17. **Batch texture preparation targets static ASTC textures only.** Prepare supported static ASTC game textures during setup so gameplay does not decode/re-encode them on ordinary loads. Existing PC-compatible textures remain unchanged. R3 defines the replacement boundary. Runtime conversion of genuinely dynamic or modified contents is acceptable if it has no noticeable performance impact; small asset counts alone do not prove low cost, so account for bytes, conversion frequency and bursts. ASTC is a GPU texture format, not an ARM CPU instruction format. Avoid unnecessary conversion on PCs by selecting prepared natively sampled representations, while retaining original ASTC on hardware that can use it directly. The claim of eliminating runtime conversion must state its static-asset coverage.
18. **Low latency is preferred, with a small tradeoff allowed for smoothness.** Controller and gyro must remain responsive and must not feel sluggish. Do not turn this into an arbitrary fixed buffering allowance: evaluate motion-to-display/input response, queue depth and pacing with FG on/off and during slow periods. This does not reauthorize the retired one-frame-ahead implementation. A numerical latency budget remains to be set.
19. **Preserve the vanilla visual experience and all visual effects.** Small compromises such as suitable texture compression are acceptable when they do not meaningfully reduce perceived quality. Keep original mip/detail coverage and correct material behavior; evaluate compression against decoded original assets, including alpha, normals and packed material channels. Do not meet sustained budgets by dropping effects, missing geometry, broken culling, conspicuous pop-in or stale visual data. The user separately accepts brief, localized cosmetic omissions for rare preparation misses when eliminating them would have disproportionate installation/loading cost. Correct complete output must return promptly; this exception is not the normal rendering policy. Quality tolerances and texture exceptions require representative visual checks later.
20. **Spend preparation time where it prevents visible disruption, with diminishing returns respected.** Longer installation, initial save loading and normal area-transition loading sequences are acceptable when they substantially reduce gameplay stalls. During visible realtime world rendering or player control, avoid hitches and performance dips. A disabled input flag alone does not turn a realtime cutscene into an acceptable loading interval. The user would prefer a small brief cosmetic compromise over, for example, doubling preparation/loading time to cover the final rare 1–2% of stutter cases. This is an illustrative tradeoff, not a measured coverage threshold or a license to regress ordinary preparation coverage.
21. **Windows 11 is the expected target; AMD and NVIDIA GPU support are required.** Explain and obtain the user's decision before adopting a design that necessarily breaks compatibility with older Windows versions. Windows 11 priority is not blanket authorization to remove older compatibility. Intel GPUs are a possible future target and must not constrain the initial architecture; this does not require deliberately blocking them. Exact supported GPU generations, driver/API capabilities and Windows build floor still need definition. No newly inferred non-Windows support commitment is made.
22. **Prefer settings changes during play through one explicit Apply action.** Selection edits pending preferences; it must not immediately toggle the running renderer. Resolution, upscaler and FG changes should apply without restarting where practical. A small controlled pause at Apply is acceptable. If a restart-only design has concrete advantages, explain the saved complexity, cost or limitation before choosing it; restart gating is not an automatic default. A failed Apply must report the actual running state rather than displaying the requested combination as successful.
23. **No sustained performance degradation from session history.** Visiting many areas and returning to the same scene must not progressively reduce performance. Compare equivalent scene/time/camera/settings and account for warm caches and background activity. Bounded useful caching may grow; unbounded retained resources, repeated conversion, increasing scans or unreclaimed per-area state are not acceptable. Visual acceptance includes the original features/fidelity and appropriate reconstruction behavior: when the selected reconstruction technique replaces anti-aliasing, do not also run the vanilla SMAA pass over it. Do not apply that removal indiscriminately to a spatial-only scaler that still needs an AA policy.
24. **Performance regressions are acceptable only briefly for a justified proof of concept.** A slower prototype needs concrete evidence of a route beyond the current baseline, preferably substantially beyond it; an assertion that the foundation is cleaner is insufficient. Before such a prototype, define its allowed slowdown/scope, limited evaluation period, measurements and exit decision. The user has not supplied numeric thresholds or dates. Do not keep building indefinitely on unexplained worse performance or make it the player's baseline by default.
25. **Use multithreading to shorten the critical path and prevent avoidable overload of one core.** Distribute independent preparation/recording/maintenance work while honoring guest execution, CPU/GPU ownership and submission dependencies. Avoid a single thread accumulating unrelated serial responsibilities. Worker count and task granularity should adapt to useful parallelism and available resources. Equal core utilization is not the metric: duplicated work, contention, oversubscription and extra synchronization can make a busier CPU slower. Measure the last dependency delaying useful submission and the resulting frame time.
26. **Preserve a viable path to future one-frame-ahead rendering.** Do not implement it as an initial goal or retain the current unsafe mode merely for compatibility. Design identities, frame-associated snapshots, completion tracking and resource lifetimes so a later bounded overlap mode can be added without replacing the core again. Do not bake in the assumption that game, recording, submission and presentation always operate on the same mutable frame state. Use minimal frame/epoch concepts needed for present correctness and future extension, not speculative always-on extra copies. A design that prevents later overlap requires strong comparative evidence and an explicit user review; it cannot be justified solely by simplicity.
27. **Controller prompts and glyph replacements are required; general mod support is not an initial design requirement.** Preserve the supported controller-specific interface assets and their preparation, selection, identity and update behavior. Other texture replacements, asset mods and gameplay/code mods are incidental compatibility, with no dedicated initial support promise, QA matrix, editor/tooling requirement or obligation to preserve every old mod hook. Do not deliberately introduce architectural barriers to their future support unless there is a concrete, compelling reason presented to and accepted by the user. Incidental unsupported cases do not require delaying the core; knowingly adopting a design that forecloses support requires that separate decision. Avoid speculative mod infrastructure merely to keep a hypothetical possibility open.
28. **Supported PC visual additions are seamless resolution, upscaling, frame generation and anisotropic filtering.** Change the resolution of affected framebuffers together and use actual game/render motion data for reconstruction and frame generation. Preserve game-authored visuals and ordinary resource, lighting and depth behavior. Project-specific ambient occlusion, extended draw distance and shadow enhancements, including shadow-resolution overrides, receive no dedicated implementation, testing or acceptance gates in this work.
29. **An SSD is the supported storage baseline.** Installation/gameplay preparation and streaming may target SSD behavior. Mechanical-drive compatibility is incidental; do not add HDD-specific scheduling, prefetch or quality compromises. No particular SSD interface or generation has been required. SSD installation does not eliminate the need for bounded I/O, appropriate batching, incremental preparation and smooth handling of ordinary contention. Representative storage performance and free-space requirements remain to be determined.

### Applying settings as a coherent change

The Apply button is the agreed user interaction. Keep editable requested preferences separate from effective runtime state. Validate the full requested combination and capabilities, determine what resources and histories need recreation, and estimate transition memory before starting. Apply changes together at a safe boundary; present a controlled pause when needed rather than permitting consumers to observe a half-switched configuration. Reset temporal history where the change makes it invalid and ensure FG receives matching dimensions, frame identities and resources.

Keeping both old and new resource sets live may make transitions faster but can exceed the minimum-memory budget. Where necessary, drain relevant work and release/recreate resources during the allowed pause rather than allocating both sets unconditionally. Establish a defined recovery configuration and accurate error reporting if recreation fails. Do not promise cost-free rollback after releasing the old set. Cancel discards unapplied edits. Persistence follows the agreed migration/configuration policy and must not claim failed changes are effective.

This contract does not prescribe a swapchain or synchronization implementation yet. It makes live changes the preferred outcome and requires a concrete rationale for each restart-only exception.

The user approved the following interaction details: selections stay pending until Apply; closing F1 keeps pending selections for the session without applying them; Cancel changes restores active values; Restore defaults changes pending selections and still requires Apply. Persist only successfully applied preferences. Display changes that could make the screen unusable require a Keep these settings countdown and automatic reversion if not confirmed; ordinary changes such as volume do not. Treat a provisional display result as unconfirmed until accepted. If a restart is required, explain that before Apply and never restart automatically. Failed changes must leave the menu accurately showing the previous working state or the defined recovery state.

### Preparation and exceptional fallback policy

Installation should perform reusable expensive conversion and known shader/pipeline preparation. Initial save loading and genuine loading transitions can prepare the destination's working set, completing required work before the world becomes visible or control resumes. Unbounded RAM use is not justified by a longer loading allowance. Ordinary traversal remains a gameplay workload, even if streaming occurs in the background.

For a rare miss after play begins, prefer a valid, visually close temporary representation while the exact result is prepared. A brief omission in a small cosmetic area is acceptable if it is less disruptive than the stall and does not meaningfully change the experience. Do not use unsafe stale data as a fallback. Any alternative draw must preserve required nonvisual work and depth/visibility semantics; it cannot blindly discard a command that also affects later rendering or game behavior.

Recommended limits, to be detailed with the implementation: do not hide the player, enemies, navigable geometry, interactions, aiming information or essential HUD; do not permit a screen-wide flash or a large lighting/shadow failure. These are proposed guardrails for the user's limited cosmetic allowance, not a claim that every texture has already been classified. Define eligible classes, maximum duration/screen coverage and a deadline policy before shipping a fallback. A fallback that repeatedly reappears on ordinary revisits indicates missing preparation, invalidation or residency work and must be investigated.

Record fallback frequency, duration, affected coverage/class, cause and exact-result readiness alongside stalls avoided and preparation time. Do not claim hitch elimination from FPS alone while concealing repeated missing output. Include DLSS history/motion/depth behavior when replacing temporary content so a short substitution does not leave a longer trail or flash. Correct rendering takes precedence where no safe cosmetic substitute exists; improve preparation for those cases rather than assuming omission is allowed.

### Implications for the earlier cleanup decisions

The 16 GB RAM requirement replaces any earlier assumption that the project may freely raise its memory floor. Full texture detail and removal of reduced-mip modes remain approved. Meeting both requires prepared formats, bounded residency and staging, safe reclamation and reliable reuse; it cannot be achieved by retaining every resource indefinitely. Large memory systems should retain more useful work, not receive a different set of correctness rules.

The upscaling/FG and microphone requirements are preservation checks for every affected removal. Removing HDR display output does not remove high-precision scene inputs used by reconstruction. Removing current one-frame-ahead replay does not remove required previous-frame motion history, safe parallelism or presentation overlap, and must preserve the agreed extension path for a future correct overlap mode.

No fixed RAM/VRAM partition, worker count, allocator, prefetch window or cache size has been selected. These goals establish what the later design must account for, not which mechanism it must use.

### Automatic resource adaptation

Apply this policy to installation and gameplay. A machine with abundant installed RAM may have little presently available; a nominally smaller machine may have enough headroom for more overlap at a given moment. Budget CPU-side residency, queued jobs, scratch allocations and GPU-side resources from current pressure and the requirements of admitted work. Do not infer GPU headroom solely from dedicated capacity, or RAM safety solely from free physical bytes; account for committed allocations and pending work that has reserved a budget but has not allocated yet.

Prefer resource/operation metadata, explicit dependencies and shared policy over per-scene guesses, machine-name special cases or duplicated magic thresholds. Derive sizing from actual formats, dimensions, resource lifetimes and measured cost where practical. Bounded defaults, safety margins and capability-specific handling remain necessary; avoiding hardcoding does not mean removing all limits or replacing verified correctness rules with heuristics. Keep policy constants centralized, documented and observable, with no requirement for player tuning.

Adapt smoothly rather than reacting to every small fluctuation. Use bounded monitoring outside draw hot paths, pressure bands and hysteresis, conservative growth, and prompt reduction of optional work under sustained pressure. Account for jobs already in flight before admitting more. First reduce speculative preparation, batch/concurrency expansion and optional retention; reclaim only resources safe to release after all CPU/GPU users finish. Preserve the immediately required working set and useful motion history. Avoid synchronized cache purges, allocation bursts and repeated evict/reload cycles that turn adaptation itself into hitching.

Track whether additional memory or workers actually improve throughput. Stop growing when extra retention or concurrency has no useful return or another resource is saturated. When memory becomes available again, recover gradually without user action. A supported configuration must remain correct under ordinary background activity; if essential resources genuinely cannot fit, report the limitation rather than corrupting results or silently dropping required quality. Define the expected background-load envelope during acceptance planning rather than promising performance under unlimited external contention.

This is an approved design goal, not a finalized control algorithm. The choice of pressure signals, sampling cadence, margins, admission rules and reclamation ordering belongs in the core design review. Validate both shrinking and growing headroom, not just a quiet machine at startup.

## Prepared texture replacement scope

Installer conversion is a future implementation packet, not part of the current first resource-path replacement. Design prepared texture data as an explicit input to the resource path now; implement the installer producer and runtime consumption together later, using the same resource identity, freshness, lifetime and budget rules rather than a separate ownership/cache system. The agreed direction is:

- Convert only eligible static ASTC source textures. Leave existing PC-compatible formats unchanged; dynamic and GPU-written textures retain their runtime path. Preserve original mip levels, layers, color interpretation and required channels. Keep native ASTC when supported.
- Use BC7 as the default candidate for static ASTC colour textures, subject to quality validation. Normal maps and other data textures require verified channel usage and compatible shader interpretation before choosing a representation; do not assume every normal map can become BC5. Prepare sensitive textures uncompressed when recompression would violate the visual/data requirements; this still avoids runtime ASTC decoding.
- Do not impose a blanket resolution cutoff. Prioritize larger eligible textures initially, accounting for all mips/layers, but include smaller eligible textures as coverage expands because their combined loading bursts can matter. Preparation eligibility depends on content and correctness, not dimensions alone.
- Leave guest bytes and descriptors intact. Associate them with a prepared host representation rather than replacing source payloads that use different block sizes/layouts.
- Identify content and interpretation independently of its temporary guest memory address. Establish the association on asset preparation/load or first validated use; never hash entire textures at every draw.
- Invalidate associations when contents change. Cache identity includes source content, dimensions/layout interpretation, representation, encoder/decoder and policy versions, and the effective source selection. This must cover supported controller prompt assets and updates. General mod precedence/support is not a separate initial requirement; reuse an existing compatible mechanism where practical without expanding the scope to a mod platform.
- Bound and resume installation work. Keep derived game content local and outside version control. Do not create a duplicate whole game tree or unbounded working copies.
- On a cache miss or unsupported asset, use a defined exceptional path and count the miss/reason. The limited cosmetic fallback policy may cover eligible cases while preparation finishes; it does not authorize arbitrary draw dropping or stale texture reuse. Essential results still require correct materialization before use.
- Measure coverage by asset class and byte weight, plus runtime misses. Installation success alone must not claim every dynamic texture is prepared.

Encoding quality, installation-time budget, disk budget, fallback format, support for unusual texture classes and when optional rebuilding occurs remain design decisions. BC7 does not reduce memory relative to existing BC3; it primarily offers a different quality tradeoff at that footprint. Conversion avoidance, resident size and reclamation are separate outcomes.

### GPU assisted preparation and overlapping installation work

The user proposes GPU-accelerated texture compression so installation stages can use different components concurrently instead of adding their full durations serially. Evaluate this as a preferred opportunity, subject to the same quality and memory requirements. GPU BC7 encoding is an available technique; the encoder/library and quality settings are not selected yet.

Use a bounded preparation pipeline: read/decompress and identify source assets, canonicalize layout and decode ASTC as needed, encode appropriate textures on the GPU, validate/store completed results, and release intermediate storage. Shader translation, generated-code compilation and driver pipeline creation may overlap eligible texture batches when their dependencies and budgets permit. BC7 encoding alone does not eliminate the preceding extraction/deswizzle/decode work. Assign decoding to CPU or GPU based on measured total throughput rather than assuming a fixed division.

Coordinate CPU workers, GPU batches, system-memory commitment, VRAM scratch/staging and disk I/O under a shared installation budget. Separate execution components still share memory and transfers; driver compilation can also contend with preparation. Use backpressure so a fast producer cannot accumulate a game's worth of expanded textures while waiting for the next stage. Process bounded batches including all authored mips/layers, persist completed results incrementally, and resume only incomplete/incompatible work. Reserve enough CPU capacity to feed/drain the GPU instead of assigning every core to shader compilation.

The user clarified that installer support for 16 GB means successful, practical operation at that capacity, not a fixed ceiling imposed on larger systems. Automatically expand concurrency, batch sizes or useful intermediate retention when available memory and measured throughput justify it. On constrained systems, reduce overlap and process smaller batches rather than failing or relying on heavy paging; aim to avoid a large installation-time penalty. Larger systems may use substantially more RAM for meaningful speed improvements, while preserving headroom and shrinking the working set under pressure. Do not scale consumption mechanically with installed RAM when CPU, GPU or storage is already the limiting resource. No manual memory tuning should be necessary. Output quality and preparation coverage should be the same across memory capacities.

Evaluate GPU and CPU encoder paths at the accepted visual quality, checking source color interpretation, alpha and material channels. Faster encoding does not by itself establish equivalent quality. A CPU fallback may preserve installation support when GPU encoding is unavailable or fails; whether it is needed for the final hardware floor remains a support decision. An offline helper may use an API different from the runtime renderer if its output and deployment contract are suitable; this does not require changing the game's graphics API.

Compare end-to-end serial and overlapped preparation time, peak RAM/VRAM, temporary disk use and output quality on representative low/high-memory systems. Do not claim that new texture preparation is free or hides entirely behind compilation until those measurements exist. The goal is to overlap independent work and reduce total installation time without recreating the memory pressure the runtime redesign is intended to remove.

## Verification plan for later implementation

These are future acceptance requirements. They do not authorize game launches during planning or fix a benchmark run count before the candidate exists.

**Static and offline checks:** compile the supported runtime/translator/installer; verify removed symbols, configuration readers, patch sites, environment bypasses and packaged artifacts; exercise migration/redaction with synthetic values; test renderer contracts for subresources, stale identities, range writeback and deferred destruction. Existing useful starting points include `runtime/cfg_probe.c`, launcher tests, mouse checks, prepared-texture checks, shader-cache validation and pipeline-cache file checks. Add behavior-focused tests where coverage is missing.

**Shader and build checks:** rebuild generated code through the generator after guest patch changes; never reuse generated objects whose patch identity differs. Apply translator patches cleanly and verify support layouts. Reject incompatible shader carry and stale prepared pipeline recipes. Reuse unaffected caches where compatibility allows it. Removing a recipe must remove it from preparation enumeration as well as gameplay. Generated C and shader headers stay ignored; run `python tools/check_content.py --staged` before a commit.

**Correctness sessions, when authorized:** menus, boot/load/save/restart, transitions, controller and retained test input; SDR reconstruction/FG with bloom, HUD, transparency and motion vectors; close/distant textures and mip transitions; CPU/GPU-mutated resources and aliases; all four benchmark scenes; area revisits. Check the previously problematic lighting/shadow angles and windmill/NPC motion when the changes touch their paths. Do not substitute screenshots for a timing check or lack of a crash for rendering correctness.

**Performance acceptance:** first compare at equivalent visual quality and fixed configuration. Use compact frame records and existing route/camera checks, warm-cache acceptance, compressed logs and source/build/config identities. Preserve cold preparation observations separately. Report average/median FPS and lows plus the important route windows. For core integration, measure fresh-session versus multi-area-return behavior, allocations, uploads, cache misses, conversion counts and waits that actually delay submission. Long-session degradation is a release failure. A slower proof of concept must satisfy the bounded regression/evidence policy above and must not become an indefinitely deferred optimization project. No large repeated benchmark matrix for each deletion; use targeted correctness checks, then an integrated comparison at a useful milestone.

**Data and rollback:** retain a reproducible Legacy executable/checkpoint and minimal configuration backup; share immutable game inputs and compatible caches where safe. Do not share a cache file concurrently between writers without an established safe protocol. Keep personal saves protected before future save swaps. Delete transient screenshots, temporary capture data and staging files after review; retain compact findings and the minimum reproducible evidence. Roll back through a prior build/commit, not a permanent hidden switch restoring every retired subsystem.
